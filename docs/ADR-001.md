# ADR-001: Domain-Driven Design Folder Structure

## Status
Accepted

## Context
In early 2023 the team decided to adopt a more structured approach to organizing the Next.js application. The codebase was growing and we wanted to avoid the common "everything in `app/`" anti-pattern.

## Decision
We introduced a layered folder structure inspired by Clean Architecture and DDD:

- `_domain/` — Pure business logic, no framework dependencies
- `_adapter/` — Infrastructure concerns (DynamoDB, third-party APIs)
- `_di/` — Minimal dependency injection using a curry helper
- `_uiFragments/` — Shared presentational components
- `_services/` — Cross-cutting concerns (planned, not yet implemented)

Each feature lives under `_domain/<feature>/` and contains `model.ts`, `repo.ts`, `index.ts`, and a `useCases/` folder.

## Consequences

### Positive
- Clear separation of concerns
- Business logic is framework-agnostic and testable in isolation
- New developers can find feature code quickly

### Negative
- Verbose for small features (a 3-page shop has 7-line use cases)
- `_services/` was never needed; the DI helper proved sufficient
- Import paths are deep (`@/_domain/cart/useCases/addToCart/ui/AddToCart`)

## Alternatives Considered

### tRPC
Rejected because the team wanted to keep the option open for future mobile clients that might not share the Next.js backend. A REST-like boundary (Server Actions) felt more portable.

### Feature-based colocation inside `app/`
Rejected because it mixes routing concerns with business logic. The `app/` directory should remain focused on Next.js-specific code (pages, layouts, API routes).

## Notes
- Revisited in Q2 2024. Team still happy with the structure.
- The `_services/` folder may be removed in a future cleanup if it remains unused.
