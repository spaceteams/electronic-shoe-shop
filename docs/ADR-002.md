# ADR-002: Eventual Consistency for Inventory Sync

## Status
Accepted with reservations

## Context
When an order is created, we need to decrement product inventory. We have two options:

1. **Transactional (strong consistency):** Update inventory in the same request that creates the order, using a DynamoDB transaction.
2. **Eventual consistency:** Fire an async event via DynamoDB Streams → SQS → Lambda and update inventory there.

## Decision
We chose option 2 (eventual consistency) because:
- The ERP system integration is already async and unreliable (simulated 34% failure rate)
- Inventory does not need to be real-time for a shoe shop; slight overselling is acceptable during flash sales
- It keeps the order creation path fast (no extra round-trips to DynamoDB)

## Consequences

### Positive
- Order creation remains fast and simple
- Inventory sync failures do not block the user checkout flow
- Easy to add retry logic and dead-letter queues later

### Negative
- Possible race conditions if two orders for the same product are placed simultaneously
- The inventory sync Lambda currently does NOT implement optimistic locking or idempotency
- If the Lambda fails silently, inventory stays out of sync until manual correction

## Future Work
- Add `version` attribute to inventory items for optimistic locking
- Implement idempotency key on stream records to prevent double-decrement
- Consider switching to transactional updates if overselling becomes unacceptable
